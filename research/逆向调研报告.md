## 二、独家逆向成果（本次调研新增的、别人没有的资产）

### 1. Cocos Creator 3.8.8 官方 API 契约（从 `app.asar` 内提取）

`app.asar` 841MB，头部 19.5MB（超过 REA 的 16MB 解码预算 → 需按前缀收窄）。
逐前缀提取后拿到 **896 个文件 / 504 个 d.ts**：

| 路径 | 内容 |
|---|---|
| `node_modules/@cocos/creator-types/editor/**` | 完整编辑器 API 类型契约（13 个频道的 `message.d.ts`） |
| `platforms/runtime/@types/editor.d.ts` | 1407 行 —— **扩展工程实际注入的那份** |
| `modules/editor-extensions/@types/editor.d.ts` | 仅 6 行（转发到 creator-types） |

### 2. 官方消息频道表（13 个）

`asset-db` / `builder` / `engine` / `information` / `preferences` / `preview` / `program` / `programming` / `project` / `scene` / `server` / `device` / `extension` —— **没有 `console` 频道**。

`scene` 频道 53 条消息、`asset-db` 22 条。参数形状逐条对齐到 `EditorMessageMaps[J][K]['params'|'result']`。

> **重要纠错**：`Editor.Scene` / `Editor.Node` / `Editor.Component` / `Editor.Pkg` / `Editor.Console` 在 3.8.x **全部不存在**（2.x 遗留或臆造）。只能走 `Editor.Message.request(channel, message, ...args)`。

### 3. `.ccc` 编译格式逆向（本次最有技术含量的发现）

Cocos Creator 3.8.8 用**定制版 Electron**（31.3.1），编辑器内部模块编译成 `.ccc` 二进制（1037 个 @editor/*.ccc），高熵加密、无字符串、无 magic。

反查 `/node_modules/@editor/creator/dist/require.js`（明文 JS）拿到加载器：

```js
const cccFunction = function (r, e) { ... loadCCC.call(this, e = t, ...o) };
const loadCCC = (e, ...t) => compiler.test(e, ["exports","require","module","__filename","__dirname"], {filename:e}, ...t);
Module._extensions[".ccc"] = cccFunction;
```

`compiler = process._linkedBinding("electron_common_compile")` —— 实测该绑定在 Cocos 的 Electron 里**只有一个 `test` 方法**（原生 Electron 的是 `compileFunction` 等 8 个方法，Cocos 替换掉了）。

用 `ELECTRON_RUN_AS_NODE=1` 直接跑 Cocos 的 Electron 存根即可调用该绑定：

```bash
ELECTRON_RUN_AS_NODE=1 "/Applications/Cocos/Creator/3.8.8/CocosCreator.app/Contents/MacOS/CocosCreator" probe.js
```

`test` 需 10 个参数（文件名 + 参数名数组 + options + exports/require/module/filename/dirname/process/global）。这意味着**在 Cocos 自己的运行时里可以加载并执行任意 `.ccc` 模块**——是后续深挖编辑器内部实现的入口。

## 三、实测缺陷清单（这是本报告最有价值的部分）

| 错误调用 | 正确调用 |
|---|---|
| `scene:add-reference-image` | `reference-image:add-image` |
| `scene:remove-reference-image` | `reference-image:remove-image` |
| `scene:switch-reference-image` | `reference-image:switch-image` |
| `scene:refresh-reference-image` | `reference-image:refresh` |
| `scene:query-reference-image-config` | `reference-image:query-config` |
| `scene:query-current-reference-image` | `reference-image:query-current` |
| `scene:set-reference-image-position/scale/opacity` | `reference-image:set-image-data` |
| `scene:clear-all-reference-images` | `reference-image:remove-image` |

另有 `scene:query-grid-visible`（应为 `query-is-grid-visible`）、`scene:query-is-dirty`（应为 `query-dirty`）、`scene:change-view-mode-2d-3d`、`scene:new-scene`、`scene:revert-prefab`、`asset-db:query-asset-depends`、`builder:query-build-options` 等 6 个也不存在。

### 3.2 DaxianLee：README 与实现严重脱节 + 无鉴权

- **无鉴权 + `Access-Control-Allow-Origin: *` + 绑 127.0.0.1** ⇒ **任意本机网页的 JS 都能 POST `http://127.0.0.1:3000/mcp` 驱动编辑器改场景**（浏览器对 localhost 的 CORS 放行）。
  实测 `dist/mcp-server.js` 中 `authToken`/`timingSafeEqual`/`Bearer` 计数**均为 0** —— 确认不是「dist 比 source 安全」。
- **硬编码开发者绝对路径** `path.resolve('/Users/lizhiyong/NewProject_3', fsPath)` ⇒ 可读项目外任意文件。
- README 列了 **10 个不存在的工具名**，**24 个真实工具完全没提**。
- `tool-manager.ts` 兜底工具表全是死代码（camelCase 名 vs 真实注册名）。
- 8 个编辑器消息在 3.8.8 不存在（`scene:query-performance`、`scene:apply-prefab-link`、`scene:connect-prefab-instance`、`scene:set-prefab`、`scene:set-prefab-connection`、`scene:load-prefab-to-node`、`scene:delete-component`、`scene:undo.record`、`asset-db:open-asset-external`、`asset-db:write-asset`）。

### 3.3 listar：最规范，但缺事务

- 唯一做到**逐工具静态安全策略登记**（72 readOnly / 81 mutating / **36 需 confirm** / 7 open-world），且**双向强校验**：加新工具漏写策略 → 启动直接崩。
- 但**没有把 `scene:snapshot` / `snapshot-abort` 编排成事务** ⇒ 多步写操作中途失败 = 场景半改状态。
  （DaxianLee README 吹的「snapshot 原子回滚」是**闭源 Pro 版**，开源版没有。）
- 2 个消息在 3.8.8 不存在：`scene:query-performance`、`scene:query-hierarchy`、`scene:check-missing-assets`。
- 工具名 camelCase 混排（`sceneAdvanced_` / `sceneView_` / `referenceImage_` / `assetAdvanced_`）。

### 3.4 家族 B：离线编辑器的 8 个坑

1. `writePrefab` 直接 `writeFileSync` 覆盖 → **无 tmp+rename**，写中断留截断文件（而它的注册表写入反而做了 tmp+rename）。
2. `ensure-meta` op 直接写盘，**绕过内存事务** → batch 失败后 `.meta` 残留。
3. `prefab_query` 的 selector enum 只有 `['tree','node','find']`，CLI 支持 5 种 → **走 MCP 拿不到 field/overrides 查询能力**。
4. `prefab_edit` / `prefab_batch` **无 dryRun**。
5. stdio 消息**并发执行无串行化**（`handleMessage` 是 async 且未 await）。
6. 转发 JSON-RPC `id: Date.now()` → 同毫秒并发可重复。
7. `Editor.Package.disable/enable` 参数是**绝对路径不是 name**，传 name 静默不生效。
8. `execSync('find ...')` 扫 `.meta` → **Windows 不兼容**；`wmic`/`lsof` 同样只适配单平台。
9. 离线改完编辑器不感知，不 reimport 的话**编辑器下次保存会用旧数据覆盖你的修改**。
10. README 列了 4 个**根本没实现**的工具（`preview_open_browser` / `preview_refresh_browser` / `preview_screenshot` / `preview_eval_js`）。

### 3.5 家族 C

- `lwsinclair/czh2774`：**`OPEN_SCENE` 必然失败** —— `LogBridge.ts` 调场景脚本的 `openScene`，但 `mcpSceneScript.ts` 根本没导出它（grep 0 命中）。正确做法（`Editor.Message.request('scene','open-scene',uuid)`）躺在**死代码** `SceneService.ts` 里。
- `EditorControlHandler.js` 是幻觉 API 必崩模块（require 不存在的路径、调不存在的 `console` 频道、用不存在的 `Editor.Message.addListener`），且无人引用。
- **TCP 无分帧**：JSON 粘包/截断即抛错。
- 端口 6400 与 Unity MCP 冲突（作者自己注释写了）。
- `shiliyu1991`：**任意 JS 执行**（主进程 `new Function('Editor','require',...)` + 场景进程 `new Function('cc','director',...)`），无沙箱、无白名单、无二次确认。
- 两家都**无应用层心跳、无自动重连**（`max_retries` / `reconnect_backoff` 声明了但零引用）。

### 3.6 全家族共性

| 坑 | 影响 |
|---|---|
| 默认端口 3000（三家都是） | 同时开两个项目必冲突 |

## 五、我们的设计取舍（每个决策的依据）

| 决策 | 依据 |
|---|---|
| **stdio 零依赖，不用官方 SDK** | listar 的 SDK 最规范但带来 npm 依赖；harady/DaxianLee 手写都缺协议完整性。我们手写了**完整**协议实现（版本协商/能力/三件套/list_changed/错误契约），同时保留零依赖零摩擦 |
| **工具收敛到 48 个** | harady 从 166 收敛到 64 是被验证有效的方向；listar 的 153 个让描述 token 爆炸。我们按「一工具一事」收敛，描述里写清「何时用/何时别用」 |
| **消息白名单 + 别名纠错** | 直接针对 harady 的 10 个全错消息。模型如果照旧教程调用，给的是「正确名是 X」而不是 not found |
| **节点三态解析** | 现存实现里「先查 uuid 再调用」是失败率最高的一环；harady 的 node-resolve 方向对，我们扩到全工具 |
| **场景事务** | 补 listar 与所有开源版都缺的「多步写失败回滚」，用官方 `scene:snapshot` / `snapshot-abort` 原语实现，不自己造轮子 |
| **不提供任意 eval** | 家族C 的 `new Function` 等于把任意代码执行交给模型。改用 `execute-scene-script` + **固定方法白名单** |
| **离线编辑用「延迟写盘」而非回滚日志** | 抄家族B 的聪明设计（失败前从不落盘 = 天然免回滚），但补上它漏掉的 tmp+rename 原子写与 ensure-meta 事务化 |
| **多文件批量用两阶段提交** | 家族B 的延迟写盘只保证**单个文件**原子 —— 逐个文件「执行+写盘」时，第 3 个失败则前 2 个已落盘，调用方却以为什么都没发生。我们把 `editPrefab` 拆成 prepare/commit：阶段 1 全部文件只准备不写盘，阶段 2 才提交，提交中途失败再用 prepare 阶段记下的 backupContent 回滚 |
| **路径写入一律拒绝原型链** | `property: "a.__proto__.x"` 能一路写到 `Object.prototype` 上，**污染整个进程**（实测 `({}).x` 变成 PWNED）。prefab 里不可能有 `__proto__`/`constructor`/`prototype` 这三个字段名，直接拒；另加「末段只存在于原型链上」（如 `toString`）也拒 —— 那种写入只会生成引擎不认的字段，报成功但数据是垃圾 |
| **危险操作 confirm 写进 schema.required** | 抄 listar 的机制（模型绕不过），并加执行期二次校验（不只靠 schema） |
| **知识库工具** | 抄 VberAI Pro 的概念（闭源无法验证），我们自己按 Cocos 3.8.8 文档整理成结构化数据 |
| **私有 Bridge 与 MCP endpoint 分离** | 抄家族B：协议只在 hub 实现一次，多编辑器聚合/工具面/安全策略都在那边 |
| **冒烟测试把「引擎缺陷」与「真回归」分开记** | 引擎侧 scene 频道中毒（6.14）会让后续几十个场景检查以**同一条信息**失败。算成「失败」等于把一个根因变成几十个症状，真正的回归会被淹没。所以只认**精确**的错误特征、其余仍算失败；跳过项必须显式列出，「本轮没测到」和「测了没问题」不能混为一谈 |
| **跳过必须有独立的退出码** | 上面那条只做一半等于白做：这两条特征是**本项目自己的健康闸门**打出来的，闸门**不区分死因** —— 引擎自己挂死与「本项目的 bug 把引擎搞挂」打出来的是同一句话。所以退出码必须分三态：**0=全通过 / 1=有真失败 / 2=无失败但没跑完 / 3=有残留 / 4=测试自身中断**。只做「失败降级成跳过」而不改退出码，等于给测试装了个会骗人的绿灯 |
| **守卫表驱动 + 「不是路径」也要显式表态** | 「哪些 op 字段是文件路径」如果靠**两份手工白名单**（hub 一份、离线散在每个 op 里），新增 op 忘了同步 → 护栏**静默失效**。⇒ 清单收敛到**唯一一份**（放在拥有 op 定义的那个模块），守卫改成**由表驱动**（执行器在调 handler 之前统一按表查）——新增 op 只要加一行，**不存在「忘了写守卫调用」这回事**。而且光靠字段名正则兜不住（`prefab`/`asset` 这类名字正则命中不了）⇒ 命中不了的字段必须进「**明确不是路径**」表并写明理由，**二选一**，两张表都没有就报错 |
| **退出码的唯一真相 + 接线也要被测** | 同一个码在不同脚本里表示两件事，CI 就读不出来（2 曾同时是「多编辑器」与「有跳过」、3 曾同时是「崩溃」与「有残留」）→ 建统一词汇表并让所有脚本引用它。更要紧的一条：**测了纯函数不等于测了接线** —— 独立复审实测，把脚本里的 `process.exit(...)` 改回旧写法，178 条用例**一片绿**，而 bug 原样复活。⇒ 只要一个决策最终影响「外部可观察的结果」，就必须有一条**执行级**的断言（spawn 脚本看退出码），中间函数的单测不够 |
| **扩展端的路径护栏也要表驱动** | 离线层改成表驱动之后，**扩展端是同一个病**：每个 handler 在函数体里手写一行 `requireAssetUrl(args.url)` —— 新增一个带路径的 op 忘了写，那道护栏就**静默失效**（代码里有护栏、注释也写着有，但实际从来没生效）。而且那份「手写枚举」的测试表**当时就已经漏了一个**（`asset.isImported` 同样过护栏，却没被写进去）—— 漏网的不是「将来才会漏」，是**现在就在漏**。⇒ 同样收敛到唯一一份 `ASSET_PATH_FIELDS`，护栏由表**自动施加**；配套「明确不需要护栏」表（判据：扩展端会不会拿它去碰文件系统 —— 只当资源库 key 传给引擎的不需要，会拼成文件路径去读/写的必须护栏），两张表**二选一**，覆盖全部「带路径字段的扩展端 op」 |
| **带 id 的 notification 必须回响应** | JSON-RPC 2.0：**带 id 就是一个请求**，服务器**必须回响应**。原来 `notifications/cancelled` / `notifications/progress` / `notifications/roots/list_changed` 这三个分支在 switch 里 `return null` —— 客户端带 id 发过来时被一起吞掉，**不报错、不超时、就是挂住**（其它未知方法都会回 `-32601`，只有这三个会静默）。⇒ 三处明确回 `-32600`，另加一层**结构化兜底**：任何方法对带 id 的请求返回 null，统一转成 Invalid Request（将来新增方法忘了回响应，也不会再静默挂住客户端）。⚠️ 后补：第四个 `notifications/initialized` 一开始漏在了那组 case 之外（落到 `default:` 回「方法不存在」）—— **四个必须并列**，漏一个就等于没修全 |
| **「是通知」只看 id 成员在不在** | JSON-RPC 2.0 的定义是「If it is **not included** it is assumed to be a notification」⇒ `id: null` 是**带了** id 的请求，服务器 MUST 回响应。把它当通知处理 = 客户端静默挂死。而 MCP 的 Base Protocol 更进一步（「the ID MUST NOT be null」）⇒ 回 `-32600` **两套规范都合规** |
| **知识库工具：index 只列真查得到的 topic；查不到必须抛错** | ① `index` 直接返回 `Object.keys(KNOWLEDGE)` 会把 `version` 也列出来，而 enum 不接受它 ⇒ 模型照着 index 调就被拒（「声明 ≠ 能用」）。⇒ topic 清单收敛到**唯一一份**，index 的列表由「enum ∩ 知识库实际有的键」**算出来**。② 查不到组件时若「不抛错、把 error 塞进返回体」，MCP 层照常标 `isError=false` ⇒ 脚本只判 isError 就把失败当成功（**假成功**）⇒ 必须 `throw` |
| **过滤器没命中必须说出来** | `COCOS_MCP_EDITOR_FILTER` 写错时 hub 会退回连**全部**编辑器实例，而「调错实例」是多编辑器场景下最高发的那类错误。这件事以前只写在一个**从不被读**的字段里 ⇒ 启动时打一条 **stderr** 警告（给人看）+ 并进 instructions（给模型看）；instructions 只有模型看得见，**用户要立刻知道的事必须走 stderr** |

## 六、⚠️ 本轮「逐工具真跑一遍」实测出的引擎行为

> 这一节来自把**每一个**工具对真机 Cocos Creator 3.8.8 跑一遍（`test/tool-smoke.js`，84 次调用 / 70 个工具）。
> 下面每一条都是**实测结论**，不是文档抄的 —— 好几条与官方描述表对不上。

### 6.1 Cocos 3.8.8 **没有**可用的回滚原语（最重要的一条）

| 组合 | 实测结果 |
|---|---|
| `scene:snapshot` → 建 2 个节点 → `scene:snapshot-abort` | 节点数 3 → 4 → **4，没回滚** |
| `scene:begin-recording` → 建 2 个节点 → `scene:cancel-recording` | 节点数 4 → 6 → **6，没回滚** |
| `scene:begin-recording` → 改 Label 的 string → `scene:cancel-recording` | 值 `ORIGINAL` → `CHANGED` → **CHANGED，没回滚** |

官方 i18n 描述表（`builtin/scene/i18n/en/contributions/messages.js`）里明明写着
`begin_recording: "Begin node recording for undo"` / `cancel_recording: "Cancel node recording for undo"`，
**但 3.8.8 的行为跟描述对不上**。

⇒ 结论：**任何声称「用 `scene:snapshot` 编排出事务回滚」的实现都是假的。**
本项目因此自己实现了 undo 日志（先记账、失败时逆序撤销），见 `hub/src/tools/transaction.js`，
并在真机上验证过（失败事务后节点数 3 → 3，第一步建的节点也被撤销）。

### 6.2 `scene:open-scene` 失败时**不 reject 消息**

实测现象：调用方一直挂起直到客户端超时；编辑器日志里是

```
Log: SceneFacadeManager.openScene timeout.
Error: [Scene] Open scene failed: 9011fda6-...
Error: download failed: import://90/9011fda6-....json?_t=..., status: 0(error)
```

根因：打开场景时渲染进程要去 HTTP 取 `import://<uuid>.json`（场景的导入产物）。
资源刚创建、引擎还在导入时这个请求失败 → 编辑器内部打了 timeout 日志，
**但消息通道那一侧既不 resolve 也不 reject**。
⇒ 必须在 Bridge 侧自己兜超时（我们用 90s，**不重试**），并把「可能是资源还没导入完」写进错误信息。

### 6.3 `console:query` 消息不存在

3.8.8 的 `console` 频道**只有 `clear`**。读编辑器控制台要用官方 API：

```ts
namespace Editor.Logger {
    interface ILogInfo { process?: 'browser'|'renderer'; type: 'log'|'info'|'warn'|'error'; message: string; stack: string; time: number }
    function clear(regexp?: RegExp): void;   // 同步
    function query(): ILogInfo[];            // 同步，不是 Promise
}
```

注意 `query()` 是**同步**的。家族C 的 C1 按 `{type,message,stack,timestamp}` 解析、
`EditorControlHandler.js` 按 `{type,message,stack,date}` 解析 —— 两个都不对，
正确字段是 `{process, type, message, stack, time}`。

### 6.4 `scene:query-classes` 的参数是 `{extends}` 不是 `{name}`

```ts
interface QueryClassesOptions { extends?: string | string[]; excludeSelf?: boolean }
```

传 `{}` 会返回**空数组**（实测），传 `{name:'cc.Label'}` 也是空数组。
正确用法 `{extends:'cc.Component', excludeSelf:true}` → 返回全部组件类。

### 6.5 三个「假成功」陷阱

| 调用 | 现象 | 正确做法 |
|---|---|---|
| `scene:remove-node`（根节点） | **返回成功**，但引擎层面不真删 | 调用方自己先比根节点 uuid 并拦截 |
| `asset-db:delete-asset`（资源不存在） | 返回 `null`，不报错 | 判 `null` 并明确告知「没删掉」 |
| `scene:remove-component`（组件不存在） | 不一定报错，可能静默无效 | 先查节点 dump 确认组件存在 |

「假成功」比报错危险得多 —— 调用方会以为已经删掉了。

### 6.6 真机 dump 的真实形状（第三轮实测，猜错就静默失效）

`scene:query-node` 的返回：

```jsonc
{
  "active": true, "locked": false, "name": "Node",
  "position": { "name":"position", "value": {"x":0,"y":0,"z":0}, "type":"cc.Vec3", ... },
  "rotation": { "name":"eulerAngles", "value": {"x":-117.9,"y":-194.9,"z":38.6}, "type":"cc.Vec3", ... },
  "scale":    { "name":"scale", "value": {"x":1,"y":1,"z":1}, "type":"cc.Vec3", ... },
  "uuid": "...", "parent": { "name":"parent", "value": {"uuid":"..."}, "type":"cc.Node" },
  "children": [ ... ], "__type__": "cc.Node", "__comps__": [ { "type":"cc.Label", "value": {...} } ]
}
```

三个必须知道的点：

1. **`position` / `scale` / `rotation` 都是 IProperty 包装**，真值在 `.value` 里。
   直接读 `dump.position` 拿到的是整个包装对象 → 类型判断、比较全错。
2. **`rotation` 是欧拉角 `{x,y,z}`（度），不是四元数。**
   写 `quatToDegrees()` 之类的转换函数属于凭想象。
3. **`parent` 的 uuid 在 `parent.value.uuid`**，不是 `parent.uuid`。
   读错 → 事务 undo 时把节点移到场景根而不是原父节点。

另外：**`RemoveComponentOptions.uuid` 是「组件的 uuid」**，官方 d.ts 还注明 `component` 是无用参数。
传节点 uuid 的话 Cocos 只会打一句 `Remove Component failed: xxx does not exist`，
而调用方若不校验就会**报告「已删除」= 假成功**。

### 6.7 `scene:cut-node` 在 3.8.8 上**不删节点**

实测 `parent` 传「父节点 uuid / 节点自己 uuid / 节点路径」三种形态，
`scene:cut-node` 之后节点在场景树里都原封不动 —— 它只准备剪贴板（效果等同 copy-node）。
官方描述写的是 "Cut node"，与行为不符。

「剪切」要自己实现成 `copy-node`（备剪贴板）+ `remove-node`（真删）；
粘贴时 source 已在剪贴板里、**不能再按场景节点解析它**（否则「剪切→粘贴」直接失败）。
实测「复制 → 删除 → 粘贴」可行，粘贴会生成新 uuid 的节点。

### 6.8 一次 `scene:open-scene` 失败会**毒死整个 scene 频道**

场景刚创建、引擎还在导入时打开它，渲染进程取 `import://<uuid>.json` 会失败
（编辑器日志：`SceneFacadeManager.openScene timeout` + `download failed: import://xx.json, status: 0`）。

更糟的是：**这次失败之后，`scene:query-node-tree` 永远不返回**（`bridge/ping` 正常）。
所有碰场景的工具会全部挂住。

⇒ 两条硬要求：
1. **所有**编辑器消息都要有超时兜底（不能只给 open-scene 加）。
2. `asset-db:query-asset-info` 在资源**还没导入完**时也返回空 ——
   不能拿它当「导入完成」的可靠信号，要靠「打开失败就重试」兜。

### 6.9「导入完成」的**唯一可靠判据**：本地 library 库产物文件

上一节第 2 条只说了「不能靠 query-asset-info」，但没给出替代方案。
本轮真机实测把答案找出来了，答案很朴素：

> 渲染进程打开场景时去取 `import://<uuid>.json`，
> 那份数据的落盘位置就是 **`<项目>/library/<uuid前2位>/<uuid>.json`**。
> **这个文件存在 = 该资源已被资产库收录 = 可以进入打开流程。**

⚠️ 精确一点说（后面 6.13 补的实测）：这个库文件其实**是源文件的副本**
（新场景库文件 2009 字节 = 源文件 2009 字节），所以它证明的是「已被收录」，
不严格等于「引擎已准备好打开它」。但作为**前置拦截**判据它是够用的 ——
「没收录」的场景打开必然失败，而「已收录」的场景即使慢也能打开（见 6.10）。

★ **补一条更晚的实测（2026-10-22）：它仍然不是「充分条件」，而且没有更强的信号可用**
- 健康编辑器上实测：`.meta` 出现、库产物文件出现、`.meta` 里 `"imported": true`
  —— **三者在同一次 50ms 采样里同时出现**（都在 52ms）。
  ⇒ `.meta.imported` **不比库文件更晚**，没有额外信息量，不能当更强的判据。
- 但「库文件存在」也**不能保证**渲染进程一定取得到 `import://<uuid>.json`：
  同一次实测里 create→open 只花 18ms 就成功，换个时机却会 90 秒超时并毒死整个 scene 频道。
- ⇒ 结论：目前**没有**可用的更强前置判据；剩下的触发器在引擎侧，
  客户端只能靠「超时 + 健康闸门 + 明确提示重启」兜。
  （这条很重要 —— 之前代码注释里写的是「有了它就能**彻底避免**挂死」，实测证明**不能**。）

在真工程上验证过（`/Users/houtao/Minimax/cocos-mcp-e2e-project`）：

```
assets/scenes/e2e-scene.scene.meta → uuid=18ab9828-451a-4736-a6fe-072eb8cccf8d
library/18/18ab9828-451a-4736-a6fe-072eb8cccf8d.json   ✅ 存在（9457 bytes）
```

**其它候选信号全部不可用**（实测）：

| 信号 | 表现 | 为什么不能用 |
|---|---|---|
| `asset-db:query-asset-info` 非空 | 资源刚创建后 **0.5s** 就返回 | asset-db 只是「记了账」，渲染进程还没导入完 |
| 该返回值里的 `imported: true` | 同样**立刻**为真 | 同上，是同一个假信号 |
| `query-asset-info` 返回 null | 资源明明在库里 | 只是还没导入完，不是「不存在」 |
| 打开失败后重试 | 第一次失败就**毒死 scene 频道** | 重试的前提是频道还活着，而它已经死了 |

⇒ 本项目的落地做法：
1. Bridge 新增 `asset.isImported` op：**直接查库文件是否存在**（不经 asset-db）。
2. `scene.open` 在发出 `open-scene` 消息**之前**先做这个检查，
   未导入完就**明确报错并拒绝**，而不是发出去把频道搞挂。
3. `scene.create` 轮询 `asset.isImported`（而不是 `asset.info`）等导入完成。

> 这一条同时解释了本项目之前「全工具冒烟 78/82」的失败：
> `scene.open` 连续 3 次失败 → 频道被毒死 → 后续 save / reload / close 全挂。
> 前置拦截把「静默毒死」变成了「一次可读的错误」。
>
> 真机复验（已固化为常驻测试 `test/real-behavior.test.js` 第 12 节）：
> 把已导入场景的库产物挪走 → `asset.isImported` 判未导入 → `scene.open` **0.0s 拒绝** →
> **拒绝之后 scene 频道仍然健康**（这条才是拦截的意义所在）。

### 6.10 `scene:open-scene` 可能要 **26~54 秒**（超时设短了就是自伤）

本轮实测：在一个**状态干净**的编辑器上，创建一个新场景再打开它，
`scene.open` 实测耗时 **26.5 秒 / 36.4 秒 / 48.3 秒 / 53.8 秒**（四次，波动很大）。

日志里能看到引擎同时在打：
```
auto refresh because script compiled or scene changed
```
—— 资产库在做自动刷新，引擎会等它。

⇒ **超时必须放宽，而且不要重试**。之前的实现是 45s × 3 次重试：
- 45s 刚好卡在「慢但最终成功」的边界上 → 被误判成失败；
- 失败之后的重试是在引擎**半开着的状态**下继续折腾 → 才真的把 scene 频道搞死；
- 3 次 × 45s = 135s，调用方白等两分多钟。

⇒ 正确姿势：**一次给足 90s，宁可慢，不要误杀，也不要重试**。
（现在的实现：单次 90s，**不重试**；hub 侧客户端超时 150s ——
最坏路径 = 探活(8) + 查资源名(5) + open-scene(90) + 失败后复探(8) = **111s**，留 39s 余量。
这个预算数字是从 Bridge **直接 export** 出来的（`sceneOpenBudgetMs()`），
一致性断言直接 require 求值 —— 不用正则解析源码，因为正则解析实测有多种静默失效：
`60_000` 数字分隔符、`60e3` 科学计数法都会让算出来的预算塌缩而断言照样绿灯。）

⚠️ 另一条不能重试的理由（见 6.11）：还有一个触发器（引擎处理「上一个场景」失败）
**前置检查覆盖不到**，那种情况下重试发生在引擎半开着的状态 ——
正是上面说的「真的会把频道搞死」的路径。

### 6.11 引擎会尝试「恢复上一个场景」，它失败时我们完全看不见

引擎日志里偶发这一行（出现在 open-scene 挂死**之前**）：
```
Warn: [Scene] Open the previous scene failed: <uuid> can not be found.
    at SceneFacadeManager.openScene (…/scene-facade-manager.ccc:1:7225)
```

`<uuid>` 是**上一次打开、但资源已经被删掉**的场景。
引擎在打开新场景前会先处理「上一个场景」，这一步失败后 open-scene 就不返回了。

⚠️ 两条实测教训：
1. **Cocos Creator 是单实例**：用 `pkill` 杀掉后再起，新进程会检测到已有实例直接退出，
   于是「重启」根本没生效 —— probe 连的还是那个旧实例，带着上一轮的脏状态。
   排查时必须核对 **pid 是否真的变了**，否则所有实验结论都是假的
   （本轮就踩过：二分实验因为编辑器没重启而出现了「时灵时不灵」的假象）。
2. **桥接层必须假设「场景频道随时可能已经死了」**。本项目的做法见 6.12。

### 6.12 场景频道「中毒」后的正确处置：快速失败 + 可行动提示 + 允许自愈

现象：`scene:open-scene` 挂死后，**整个 scene 频道不再回应**
（`query-node-tree` / `query-node` 永远不返回），但 `bridge/ping` 一切正常。

没有防护时，调用方的体验是：

| 调用 | 表现 |
|---|---|
| `scene.open` | 干等 135 秒 → 「超时」 |
| `scene.tree` | 干等 30 秒 → 「超时」 |
| `scene.save` | 干等 30 秒 → 「超时」 |

每一条都是「超时」，完全看不出真正原因是「频道死了，该重启编辑器」。

⇒ 本项目加了一道**频道健康闸门**：
1. 每次 scene 消息前先做一次探活（8s 超时，8s 缓存）；
2. **探活必须用场景状态查询类消息**，不能用 `query-is-ready` ——
   实测频道中毒后 `query-is-ready` **3ms 就正常返回**，
   而 `query-dirty` / `query-node-tree` **永久挂起**。
   用 `query-is-ready` 探活等于闸门一直显示「健康」，然后每次操作照旧干等 30 秒。
   现在用 `query-dirty`：它是场景状态查询（中毒时同样挂），但不像 `query-node-tree`
   那样要回传整棵树，代价小得多。
3. **连续两个独立探活轮次都失败**才判定频道已死 ——
   一次失败不判死（编辑器正忙时探活可能几秒不回，一次失败就永久判死反而成了新故障源）；
   而且必须是**独立轮次**：并发调用共享同一次探活（single-flight），
   否则一次「编辑器忙」会被按并发数累加成多次失败，把用户的场景功能整个锁死；
4. 探活失败的结果**必须被后来者继承** —— TTL 窗口内的后续调用直接继承失败、
   不重复探活，也不能把失败当成放行（之前把时间戳写在探活**发出之前**，
   导致探活一失败，接下来 8 秒闸门完全敞开，`failures` 永远攒不到 2 → 闸门形同虚设）；
5. 判定已死后，所有 scene 操作**立刻**失败并给出可行动提示
   （「请重启 Cocos Creator，期间可改用离线 prefab/animation 编辑器」）；
6. 每 30 秒给一次自愈机会，探活成功就恢复 —— 频道未必真的死了。
   另外「重启 Bridge」现在会**清掉闸门状态**（它以前只重启 HTTP 服务、
   不重新加载模块 → 点了按钮场景工具仍然全挂）。

### 6.13 `scene:close-scene` 在 general edit mode 下**关不掉**（之前一直在报假成功）

实测 3.8.8：引擎返回 `false`，并在日志里打
```
Warn: [Scene] Trying to close current edit scene in general edit mode is not allowed
    at SceneFacadeFSM.closeScene (…/scene-facade-fsm.ccc:1:2843)
    at SceneFacadeManager.closeScene (…/scene-facade-manager.ccc:1:8917)
```

本项目之前无条件返回 `closed: true` —— **假成功**。
模型据此以为场景已关、接着去删资源/切场景，就会踩到后面一堆说不清的问题。

⇒ 现在 `scene.close` 在引擎拒绝时**明确报错**，并说明「切换场景直接用 scene.open，不需要先关」。

⚠️ 连带影响：既然关不掉，「当前打开的场景」就一直存在 ——
所以**不能删掉当前打开的场景资源**（删了会让编辑器留下指向已删除资源的引用，
之后打开任何场景都会挂死）。Bridge 已加守卫拦下这个操作。

### 6.14 一组节点操作之后，**下一次打开场景必挂死**（本轮最硬的发现）

在干净编辑器上复现（每一步都可重复）：

```
打开场景 X（成功）
→ node.create / node.active / node.transform / node.duplicate / node.move / node.clipboard
→ 等 25 秒
→ 打开场景 Y → 90 秒超时 → 整个 scene 频道中毒
```

对照组（不做这些节点操作、只建一个节点 / 场景变脏 / 先保存 / 删掉 X）**全部正常**。

⚠️ 这意味着：**节点层面的结构性改动会让引擎的「打开下一个场景」路径卡死**。
引擎侧没有任何报错，消息既不 resolve 也不 reject。

⇒ 本项目能做的（并已经做了）：
1. **90 秒超时**（实测健康时打开场景要 9~54 秒，不能设短了误杀）；
2. 失败后**立刻**判定频道状态，给出「频道已中毒，请重启 Cocos Creator」的可行动提示；
3. 健康闸门让后续场景操作**秒级失败**而不是各等 30 秒。

⇒ 剩下的「怎么让引擎不挂」是 Cocos 自身的问题，本项目只能绕。

⚠️ **补充（第十一轮实测）：中毒的表现比「scene 频道中毒」更广 —— 整个 Bridge 会一起失联，而且会自愈。**

实测（冒烟收尾那句「切回原场景」挂死 98 秒之后）：

| 现象 | 实测 |
|---|---|
| `scene.tree` 等场景调用 | 秒级失败（健康闸门） |
| **Bridge 的 HTTP 端点** | **完全不回** —— 连 `GET /bridge` 的鉴权失败（401）都没有，直接超时 |
| hub 的心跳探测 | 报「心跳超时且无响应」 |
| 编辑器进程 | 活着（12 个子进程都在），但 Bridge 不应答 |
| **约 15 分钟后** | **自己恢复** —— `scene.tree` 重新有响应，Bridge 也活了 |

⇒ 两条重要的实践结论：
1. **「编辑器要重启才能跑真机层」不是必须，只是更快。**
   等它自愈（实测 ~15 分钟）也能继续 —— 重启只是把等待从 15 分钟压到 1 分钟。
2. **中毒期间，扩展端本地就能拒的请求也会「超时」。**
   因为请求**根本没到扩展端**（Bridge 不应答），
   所以「越界路径被拒」这类**纯本地**的护栏，在中毒期测出来也是「超时」——
   **看起来像护栏失效，其实根本没执行**。
   ⇒ 排查「护栏怎么没拦住」时，**先确认 Bridge 是活的**（`node hub/bin.js --probe`），
   否则会把「引擎挂死」误判成「自己的护栏有洞」。

### 6.15 短 uuid 的字符集含 `+` 和 `/`（漏掉会导致**间歇性**「找不到节点」）

真机实测引擎会产出这两种字符：
```
cbguKOUmRESoTWvkSFxlH+
d67EOER/ZLSLW84UxP+nMW
```
而 base64url 的字符集是 `[A-Za-z0-9_-]` —— **不含 `+` 和 `/`**。

⚠️ 后果极其隐蔽：这类 uuid 匹配不上 → 被当成**节点名**去场景树里找 →
节点刚建出来时引擎的场景树可能还没重建 → **间歇性**报「找不到节点」
（同一份代码连跑 5 轮里有 1 轮失败，极难定位）。

⇒ 两处修：
1. 短 uuid 的正则补上 `+` 和 `/`（字符集不含 `.`，所以路径穿越仍然被挡住）；
2. **按 uuid 查节点时不再查场景树** —— uuid 本身就能直接交给引擎，绕开树就没有竞态。

### 6.16 `create-node` 会忽略 `position`，而 `set-property` 生效（且有竞态）

真机实测：
| 路径 | 结果 |
|---|---|
| `node.create` 带 position | 建完回读 position 仍是 `{0,0,0}` ❌ |
| `node.transform` 设 position | 回读 `{11,22}` ✅ |

⇒ 工具声明了 position 却静默不生效 = 「假成功」。
现在 `node.create` 在建完节点后**补一次 set-property**，并**回读校验 + 重试**。

⚠️ 另外实测：`set-property` **返回时引擎可能还没真正应用** ——
紧接着回读有时还是旧值。所以「设置完就返回」也是不可靠的，
必须回读校验。

⇒ 这两条合起来是本项目最典型的「声明了 ≠ 生效了」：
**工具的每个参数都要在真机上比对一次回读值**，不能只看调用没报错。

### 6.17 其它实测细节

- **`scene:query-node-tree` 的返回不含 `__comps__`**（只有 `scene:query-node` 才有）。
  树里输出 `components: []` 会让模型误判「这个节点没有组件」—— 要么不输出该字段，要么另查。
- **Cocos 短 uuid 是 base64 字符集**（22 字符，可能含 `g`/`x`/`k`/`q` 等非十六进制字符）。
  按 hex 正则判会把真 uuid 当成节点名去树里找，必然找不到。
- **编辑器冷启动时 asset-db 还在初始化**，此时前几个请求可能整体阻塞几十秒
  （日志里能看到 `asset-db is ready!`）。Bridge/客户端的超时设置要考虑这个窗口。
- **编辑器刚启动的几秒内，场景根节点会短暂没有名字**（`readName` 返回 `<unnamed>`）。
  这时按根节点名建子节点会「找不到节点」—— 自动化脚本必须等场景就绪，
  否则会**静默跳过**一整段操作，还以为「测过了」。
- **编辑器 dump 的属性是 IProperty 包装** `{value, type, default, displayName, tooltip, ...}`，
  嵌套的属性表也要递归解包，否则模型每次读节点都要看几十行噪音。
- **`library/<xx>/<uuid>.json` 其实是源文件的副本**（实测新场景库文件 2009 字节 = 源文件 2009 字节），
  不是「编译产物」。所以它能作为「资源已被资产库收录」的判据，
  但**不能**据此断言「引擎已经准备好打开它了」。

### 6.18 引擎侧节点对象的原型链形状：`__proto__` 在它们身上**可写**

第十轮独立复审发现，本项目自己写的引擎级 `scene.script`（`extension/scene.js` 的
`setNodeProperty`）有一处**能破坏整个编辑器进程**的洞。

- **引擎节点对象的形状**：节点的属性（`position` / `active` / `angle` …）
  大多是**原型上的访问器**，不是自有属性。
  所以「属性存不存在」这一层不能只看 `hasOwnProperty` ——
  访问器**当前返回 undefined** 时它仍可写，那时 `hasOwnProperty` 会误判成「不存在」。
- **后果**：如果按路径逐段写入且不拦保留段，
  `property: "__proto__.toString"` 能一路走到 `Object.prototype` ——
  **覆盖整个进程的 `Object.prototype.toString`**，编辑器直接被破坏
  （不是「那个节点坏掉」，是整个进程的对象语义被改写）。
  用真 Cocos 形状的假 cc 节点实测：写入后 `({}).toString` 变成被覆盖的值。
- **修法**：逐段拒绝 `__proto__` / `constructor` / `prototype`；
  另外「**在对象上存在、但不是它自己的**」的末段也要拒
  （`toString` / `valueOf` / `hasOwnProperty` 这类只存在于原型链上的名字 ——
  写入只会生成引擎不认的字段，**报成功但数据是垃圾**）。
- **最要紧的一条教训**：**「prefab 侧修了」≠「这个类修完了」** ——
  同一个洞在离线层修完之后，引擎层（`extension/scene.js`）还有同款。
  ⇒ 修完一处必须按「同一类洞」**逐层再扫一遍**（解析层 / 读层 / 写层入口 /
    遍历自有属性 / 末段继承属性），而不是改完一处就收工。
